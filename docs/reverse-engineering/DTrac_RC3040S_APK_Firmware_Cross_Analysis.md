# DTrac APK ↔ RC-3040S 8051 固件交叉逆向报告

**日期：** 2026-10-24  
**目标：** 重建局域网发现、识别码、NRL2 UDP 封装及云台 GO/STOP/角度反馈的互操作协议  
**静态样本：** `dtrac.apk` (SHA-256: `120c43f5d09e307ecfd7b168676486c41984d28a2a47b83d19abae7adf04d23a`) 和之前离线恢复的 `RC_3040S_67S_8H_251217_firmware_8051.bin` (41,738 B)  
**方法：** ZIP/DEX 结构化解析、Dalvik 指令解析、静态字符串与调用点交叉引用、先前恢复的 8051 固件反汇编结果交叉核对。无 APK 安装、未知程序执行或设备操作。DEx 偏移指 `classes.dex` 文件内的偏移；8051 地址指映像加载基址为 0x0000 的代码地址。

## 1. 核心结论

1. **局域网发现已经双端闭合**：APP 将 ASCII `cmd=ping\n` 发往 UDP 广播 `255.255.255.255:60059`；MCU 固件 UDP Socket 2 监听 `60059`，识别 `cmd=ping` 并回送 `cmd=pong...` 给请求源 IP/源端口。APP 读取并保存 IP、端口、RotorID。
2. **本机 RotorID 的默认来源**：MCU 的 7B CHIPID，非易失存储偏移 `0x10..0x16`，运行时 XDATA `0x09B1`，输出时大写十六进制编码成 14 字符。第二份 7B 位于 EEPROM `0x17..0x1D`，后续用途尚需核对。
3. **APP 的 SID 的默认来源**：Android 设备标识材料 → SHA-256 → 末尾 14 字符大写十六进制；保存到 `sid` 偏好设置。该字段与 RotorID 是两个不同标识。
4. **NRL2 发送报文完整固定头可还原**：48B 头部；`NRL2` + 两位 ASCII 十进制长度 + 7B APP SID + 7B RotorID + Type `0x05` + 3B 零 + `DTrac` + 19B 零；后随原始云台指令。无线电路径另外使用 Type `0x06`，不能误用。
5. **GO/STOP/反馈**：APP 对 `RC-3040S` 分支的候选命令为 `W%03d %03d\r\n`、`S\r\n`、`C2\r\n`；接收位置数据取 `AZ=` 和 `EL=` 各 3 个字符，并更新位置值。MCU 命令解析器能识别相应 GS-232 命令，`S` 路径可停两轴。
6. **设备发现端口与 NRL 服务器不是同一目标**：APP 发现发 UDP `60059`，远程控制使用可配置的 `nrlAdd:nrlPort`；APK 的恢复默认值为 `202.141.176.2:60050`（只说明当时打包配置，不代表现在可用）。非 NRL UDP 则使用独立的 `rotorUdpAdd:rotorUdpPort`。

## 2. 双端发现证据

### 2.1 APP 发包

`Lei0;->r()V`，**DEX** `0x160A58`：

- 程序点 `0x0044`：`255.255.255.255`
- `0x0046`：整数端口 `60059`
- `0x0068`：常量 `cmd=ping\n`
- 后续通过内部 UDP 队列发包。

**确定发送的应用层字节：** `63 6D 64 3D 70 69 6E 67 0A`。这是 APP 发包路径字面量；真正从哪个本地源端口发送，由 UDP Socket 和网络环境决定。

### 2.2 MCU 接收和应答

从前一阶段还原的固件：

- `0x915B..0x916A`：W5500 UDP Socket 2 启动，绑定 `60059` (`0xEA9B`)；
- `0x8E0A -> 0x4E62 -> 0x4F20`：接收与识别 `cmd=ping`；
- `0x4F31..0x4FCF`：构造 `cmd=pong&type=RC-3040S&ip=<IP>&port=60020&rotorid=<ID>`；
- `0x4FD0..0x4FF0`：W5500 目的 IP、端口更新为请求来源并发送。

**延时：** 代码中该路径接收到请求后直接组包发送，没有证据支持人为固定延迟；实际往返时延仍需实机抓包测定。

### 2.3 APP 解析和兼容

`Lei0;->g(Llt0;)V`，**DEX** `0x160268`，程序点约 `0x0096..0x015E`：

- 对发现应答按 `&` 分割，首段检查 `cmd=pong`；
- 提取类型、IP、端口与标识，写入 `rotorTcpAdd`、`rotorTcpPort`、`rotorId` 等键；
- 类型 `1` 为旋转器、`2` 为电台的路径可以识别。旧固件的 `type=RC-3040S` 不等于数值 `1/2`，APK 源码中存在落入旋转器处理的兼容分支，但它是较脆弱的按位置/索引提取逻辑。
- 解析实际上依赖字段的**既定位置**，不是一个健壮的通用 query-string parser；SkyRoof 应按字段名称解析 `id/rotorid`、`type` 和 `port`，容忍 CR/LF 与字段顺序变化，并验证来源 IP。

**局域网发现首选协议：** `cmd=ping\n` 请求 UDP/60059，收到的 `pong` 从源地址/端口返回。不要通过发送电机动作命令测试发现路径。

## 3. RotorID 与 APP SID

### 3.1 MCU RotorID

先前已从芯片固件反汇编得到：`0x8786..0x87CE` 读取 STC8H 的 XDATA CHIPID `0xFDE0..0xFDE6`，缓存到 `0x0F18..0x0F1E`；首次初始化经 `0x53E0` 写入 EEPROM `0x10..0x16` 并复制到 `0x17..0x1D`。`0x940E` 将配置载入 `XDATA 0x09A1..0x0BA0`，`0x4FB0` 读取 `0x09B1` 并调用 `0x81FB` 编码为 14 个大写十六进制字符。

仍需区分“出厂默认等于 CHIPID”与“升级或手动修改过配置后的当前 ID”；优先以实机 `pong` 为准，勿为获取识别码执行 `AT+INIT`。

### 3.2 APP SID

APK：

- `Lr01;->I(Context)String`，**DEX** `0x198488` 附近：获取 Android ID；旧版 Android 上存在 Telephony ID 路径；否则按设备 Build 属性拼接回退材料。
- `Lr01;->J(String)String`，**DEX** `0x198558`：SHA-256、转小写 64 位十六进制字符串。
- `Lw00;->onClick()`，**DEX** `0x12B7F0`，程序点 `0x0128..0x0149`：在 `sid` 尚未有值时调用上面两个函数、转大写、保留最后 14 字符，存入偏好设置。
- `Lg10;->handleMessage()` 亦有 `sid` 迁移/重设路径，不能认为所有安装实例每次启动都会重新计算。

故 SID 为 7B 客户端身份的十六进制形式。SkyRoof 建议随机生成并长期保存自己的 7B SID，但实际 NRL 服务是否要求账户绑定/白名单仍应实机验证。

## 4. NRL2 头格式（DTrac APP 实际用法）

**云台封包实现：** `Lei0;->n(String,String)[B`，DEX `0x15FC00`，程序点 `0x0000..0x004B`。

| 偏移 | 大小 | 实际内容 | 证据 |
|---:|---:|---|---|
| 0–3 | 4 | ASCII `NRL2` | `4E524C32` 常量 |
| 4–5 | 2 | ASCII 十进制长度字符，例如 `35 32` 表示字符 `52` | `len(payload)/2+48` → `append(int)` → `Lat0.j0()` 逐字符 ASCII→HEX |
| 6–12 | 7 | APP SID，原始 7B | `sid`，14 hex chars |
| 13–19 | 7 | 目标 RotorID，原始 7B | `rotorId`，14 hex chars |
| 20 | 1 | `0x05` | 固定 28B 模板开头 |
| 21–23 | 3 | `00 00 00` | 固定模板 |
| 24–28 | 5 | ASCII `DTrac` | 模板 `44 54 72 61 63` |
| 29–47 | 19 | 零填充 | 固定模板 |
| 48+ | 可变 | 原始云台控制载荷 | 函数末尾拼接的 hex payload |

原始模板：

```
05000000445472616300000000000000000000000000000000000000
```

**无线电**用 `Lqf0;->g(String,String)[B`，DEX `0x157FFC`，相同结构但类型字节为 `0x06`。NRL 服务器的通用 Type 6/10 语义不可不经测试直接等同于 DTrac 云台 Type 5。

### 4.1 ASCII 长度字段的互操作问题

`Lat0;->j0(String)String`，DEX `0x1812B8`，逐字符转换 UTF-16 char 为 ASCII hex，没有将 `int length` 作为 `uint16` 大端序编码。因此实际为：

- 4B 载荷：总长 52 → 长度字段 `35 32`（ASCII `52`），**不是** BE uint16 `00 34`；
- 3B STOP：总长 51 → `35 31`；
- 10B GO：总长 58 → `35 38`。

若载荷达到 52B，则长度十进制变三位，固定 48B 头部会失去对齐，必须用实际数据验证限制；离线重建器目前明确拒绝此类不兼容情形。开源 `hicaoc/nrllink` 的普通解码器把偏移 4–5 视作二进制 BE uint16，但其实际检查/转发行为须分版本核对，不能由这两个实现表面相似就假设二者通用。

### 4.2 接收检查（值得 SkyRoof 改进）

`Lei0;->g(Llt0;)V`，DEX `0x160268`，程序点 `0x0037..0x0095`：

- 打开 `nrl` 选项时，数据必须以 `NRL2` 开始；
- 把报文字节编码为 hex 字符串，取字符 `[12:26]`（即原始字节 6–12）和 `[26:40]`（字节 13–19）；
- 与本地 `sid` 和 `rotorId` 比较，比较结果参与连接状态标志；
- 长度不少于 48B 时，以字符索引 96（原始字节偏移 48）取得载荷并继续处理。

**安全与健壮性：** 在该代码分支中，ID 不匹配不会统一触发无条件丢包，而是可能仍继续交付载荷给上层（尚需运行时路径验证）。SkyRoof 应主动严格验证远端 endpoint、长度、SID、RotorID、类型与载荷格式，不应照抄这种宽松接收逻辑。NRL2 两组 ID 也不是加密认证。

### 4.3 传输目标分流

`Ldi0;->run()`，DEX `0x15F22C`，程序点约 `0x041B..0x049C`：

- 网络 TCP：通过 TCP 已建立的 Socket 发送原始 GS-232 控制；
- 网络 UDP + `nrl=true`：`Lei0.n()` 封包，目的地址取 `nrlAdd:nrlPort`；
- 网络 UDP + `nrl=false`：直接发送原始命令数据至 `rotorUdpAdd:rotorUdpPort`。

`Lw00;->onClick()` 默认设置重建代码 DEX `0x12B7F0` 在 `0x006A..0x0075` 中给出 `nrlAdd = 202.141.176.2`、`nrlPort = 60050`，但不保证当前公网 NRL 节点可访问。**绝对不要把此默认远程地址替代 RC-3040S 局域网 UDP 60059。**

## 5. 位置查询、GO 与 STOP

### 5.1 APP 侧完整核心文本命令

`Lei0;->q()` (DEX `0x15FCA8`) 和 `Lei0;->o()` (DEX `0x160740`) 的 `RC-3040S` 设备类型分支编号为 8，并选择文本 `C2\r\n` 做位置查询。`Lei0;->t()` (DEX `0x160BC8`) 在同类型分支选择文本 `S\r\n` 用于 STOP。对应 STOP 由 `Ln00;->onTouch()` 多个动作分支触发。

`MainActivity;->v(Context)` (DEX `0x226C20`) 的设备类型分支 8 在 `0x00B5..0x0120` 拼接：`W` + `String.format("%03d", round(AZ))` + ` ` + `String.format("%03d", round(EL))` + `\r\n`。因此可得示例：

```
查询：b'C2\r\n'
运动：b'W181 030\r\n'
STOP：b'S\r\n'
```

这是 APP 的实际构造格式，并非仅依据 GS-232 文档的泛化推测。网络发送处存在队列/并发任务；STOP 是否插队、是否仍排在运动命令后面，需要单独按实际调度验证。

### 5.2 APP 侧位置应答解析

`Lei0;->m(String)` (DEX `0x160040`) 检查 `AZ=`，提取三个字符解析 Double，随后搜索 `EL=` 再提取三字符。对应先前 MCU `0x6579`、`0x7DD1`、`0x7E3F` 的 `AZ=ddd  EL=ddd\r\n` 预期回复；完整响应字节依然以硬件采样为准。

### 5.3 固件执行映射

先前 MCU 8051 `0x3433..0x385F` 对 GS-232 `M/W/C2/C/B/A/E/S/L/R/U/D` 做分支，`S` 经 `0x375F -> 0x98A0` 终止两轴。Motor STOP 语义在固件里有实际状态/控制位清零动作，而非纯 APP UI 标记。

**未证明的链路**：NRL 云服务器如何将 Type5 封装转发到控制板 W5500，W5500 是在 UDP 60059 的哪个分支解 NRL2、是否有中间代理/桥，以及远端 APP 与控制板断线后的 STOP 是否保证送达；这些需要分析更多固件 Socket 通路或通过受控抓包验证，不能仅因 APP 有封包函数就宣称实机 E2E 已验收。

## 6. 对 SkyRoof 的实现建议

- `DTracDiscoveryClient`: UDP 60059 发 `cmd=ping\n`，本地临时 UDP 端口接收 `pong`；按键名解析 `id/rotorid`，IP/端口白名单、来源校验、重试及超时；UI 仅显示经验证的设备。
- `DTracNrl2Codec`: 按本 APK 兼容格式构建/解析 48B 头；将 APP SID 持久化；每次校验目标 RotorID，遵循实际使用的 ASCII 长度规则并拒绝异常长度，避免擅自改成二进制 uint16；对包号、认证和兼容版本进行后续扩展。
- `DTracNativeUdpTransport`: 独立普通 UDP host/port（不加 NRL 头）；必须明确目标控制板确实识别相关 GS-232 载荷后才启用运动。
- `DTracNrlTransport`: 独立的 NRL 服务器地址/端口/身份设置；适当的会话重建和远端状态监测，避免把 UDP `sendto` 成功误判为“控制板在线”。
- `Gs232RotorCodec`: `W%03d %03d\r\n` / `C2\r\n` / `S\r\n` 和 `AZ=ddd  EL=ddd` 解析，串行和网络模式可共用；注意字符串合法性、范围、机械限位及负载长度。
- **安全性**：STOP 与 Track 的发送队列应设为两类优先级，STOP 清理旧的未发送运动命令，必要时反复确认停机及触发本地硬件急停。不可依赖单次 UDP STOP 实现失联保护。

## 7. 只读/离线可验证测试和未完成项

1. 使用 `dtrac_protocol_lab.py --demo` 验证虚构 APP SID/设备 RotorID 的离线 NRL2 报文构建和解析，无外发流量；单元测试发现响应的多种字段名、末尾 `\n` 以及 `C2/W/S` 载荷。
2. 用抓包验证 APP 的发现请求 `cmd=ping\n` 是否从临时源端口发起，以及实际 `pong` 中 `type` 和 `id` 的取值。
3. 在断开电机功率、确认位置反馈只读的条件下抓 NRL 模式实际数据，记录本地至服务器 IP/port、服务端回应/保活频率和外网重连；抓包中真实 SID/rotor ID 应打码。
4. 继续追踪 MCU 固件 Socket 3、UDP 60059 的所有非 `ping` 分支，以及其是否接收 Type 5 封包；必要时核对控制板上是否存在独立 NRL 模块。
5. 安全的台架实验依次验证 `C2`、`S` 和小角度 `W`；多 APP 时检验控制权、旧队列清理、断联超时与反馈一致性。
