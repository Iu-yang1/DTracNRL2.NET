## 1. 结论先行：没有证据把 APP 的跟踪行为等同于 ACC/DEC/JERK 或 S 曲线

在**这份特定的 Android APK**中，能够证实的应用层控制是：更新/计算目标方位俯仰 → 按设备类型格式化绝对目标角命令 → 投递到传输队列；该 APK 对 RC-3040S 的目标命令使用 `W%03d %03d\r\n`，查询使用 `C2\r\n`，停止使用 `S\r\n`。代码确有 `AT+DEMO=ON/OFF` 字符串，但是通过按钮条件分支直接发送；在该按钮回调中没有生成分阶段速度值。

不能由此得出“所有版本的 DTrac 软件都不存在加减速”。尤其当用户说的 DTrac 是 **不同版本 / Windows 客户端 / 原厂另一个安装包** 时，当前 APK **不代表**那个程序。Android APK 的滑动、传感器平滑、卫星角度连续更新也不等于电机 STEP 定时器的梯形或 S 曲线加减速。

**判断等级**：针对当前已定位的 RC-3040S 发送分支，“没有看到独立 ACC/DEC/JERK 指令或速度轨迹规划”是有控制流支持的**否定性局部发现**；针对 APK 所有可能经过混淆、反射、动态字符串和 JNI 的代码，或其他 DTrac 二进制的完整排除，**不能成立**。

## 4. “根据剩余角度自动降低速度”的三种不同情况，不能混淆

1. **应用层实际速度规划**：APP 周期计算 `target-current`，输出递减的速度量（例如 `AZ_SPD`），或按时间对目标做明确的速度/加速度限制；要找到对应状态变量、时间戳、`v/a/j` 更新与发送路径才可宣称成立。**当前 APK 的 RC-3040S 链路未找到这一闭环**。
2. **连续目标更新 + 固定速度固件追踪**：APP 定期发送新的 `W AZ EL`，卫星轨迹本身平滑，云台固件每次向目标走、到位停止。看起来可能平缓，但不代表 APP 通过 ACC/DEC/JERK 改了步进速度。**当前 APK 明确具有这条链路**。
3. **固件/电机驱动器自行限速**：APP 发送目标角或 DEMO 切换，固件或外部驱动按自身策略控制脉冲频率。只有板端定时器中断或物理 STEP 波形能确认。旧 `251217` ROM 的定时器计算已在 Stage12 分析，但不能直接替代对新 `260223_C` 的验证。

## 5. 对 SDK 和 SkyRoof 的直接影响

- **不要**因为 APK 中存在 UI 加速插值器就添加 `AT+ACC/DEC/JERK` 原生命令；当前没有协议证据。
- **不要**把 `speedThreshold=15` 直接作为减速距离或初始速度加速度阈值。
- **不要**以不停改写 `AT+AZ_SPD / EL_SPD` 的方式实现卫星跟踪阶段速度规划：旧 ROM 的 AT 写入调用过配置保存路径，存在 EEPROM 磨损和失联风险。
- 如果 SkyRoof 确实希望应用层加减速，可作为**明确区别于 DTrac 原生 AT 的新功能**，由受控 `W` 目标插值 / 运动调度器来实现，并遵守限位、STOP 优先级、角度回读真实性及 TCP 连接稳定性；但这是新设计，不应包装成已恢复的原厂算法。

## 6. 还缺什么才能恢复“原厂软件 S 曲线”

如果用户所指的 DTrac **不是这份 Android APK**，而是 PC 软件、另一个版本 APK 或包含独立控制算法的安装包，那么需要该程序的**确切二进制**才能继续恢复：其 ACC/DEC/JERK 的真实参数、轨迹周期、jerk 限幅、减速触发条件、目标改变时的再规划策略以及实际发送指令。先寻找编排函数、计时器和 TCP/UDP 发包端，不预设一定使用经典 7 段 S 曲线。若只有当前 APK，本阶段可以确认的是目标角指令/队列/DEMO 路由，尚未恢复一个可验证的应用层速度曲线规划器。
