# RC-3040S_67S_8H_251217 固件逆向分析报告（二阶段）

> 分析日期：2026-10-24。对象为用户提供 EXE 中已离线恢复的 41,738 B 8051 代码映像（0x0000 基址）。仅静态分析，未执行上传的 EXE、未连接控制板、未实际驱动电机。地址为代码地址或 XDATA 地址，除特别说明外不是 EXE 文件偏移。

## 1. LAN 发现：本地 UDP 接收 → 识别 → 定向应答

### 1.1 监听端口和协议

```
915B  MOV DPTR,#0x1023  ; Socket2 尚未打开标志
9161  MOV R5,#0x9B      ; 端口低字节
9163  MOV R4,#0xEA      ; 端口高字节
9165  MOV R7,#0x02      ; Socket 编号 2
9167  LCALL 0x94BE     ; Socket 开启
```

`0x94BE` 进一步使用 W5500 Socket 模式 UDP (Sn_MR=2)，端口 Sn_PORT=60059，打开后 Socket 状态 `SOCK_UDP=0x22`。W5500 官方说明：<https://docs.wiznet.io/Product/Chip/Ethernet/W5500/Application/udp>。

### 1.2 发现请求

只证实 `cmd=ping` 是字符串匹配标识（位于代码映像 `0xA153`）。匹配函数 `0x9378` 被 `0x4F26` 调用，返回 1 才继续组装 `pong`。不能由此证明必须带 CRLF，也不应推断请求是 NRL2 二进制包。用于纯发现的最小候选请求：`63 6D 64 3D 70 69 6E 67`（ASCII `cmd=ping`）。

### 1.3 UDP 响应寻址及应答时序

`0x4E62` 起，从 W5500 UDP RX 缓冲前 8 字节解析 4B 源 IP、2B 源端口、2B 负载长度，并把负载复制到解析缓冲区。`0x8E0A` 在接收成功后调用 `0x4E62`。

```
4F20  ... 'cmd=ping' 匹配
4F31  ... append 'cmd=pong&type=RC-3040S'
4F4B  ... append '&ip='
4F62  ... append 本机 IP
4F82  ... append '&port=60020'
4F99  ... append '&rotorid='
4FB0  ... append XDATA[0x09B1] 中的 ID
4FD0  ... W5500 Socket 2 DIPR <- UDP 请求源 IPv4
4FDB  ... W5500 Socket 2 DPORT <- UDP 请求源 UDP 端口
4FE8  ... 向 Socket 2 发送回复
```

应答文本文法（末尾有可能附加换行；需实际捕获完整字节确认）：

```
cmd=pong&type=RC-3040S&ip=<LOCAL_IPV4>&port=60020&rotorid=<ROTOR_ID>
```

**时序**：网络主循环轮询 Socket 2 就绪 `0x99AE→0x8E0A→0x4E62`，拼接报文后同函数发送，没有看见固定等待计时。延迟为 W5500 轮询、SPI、发送、ARP 等实际耗时，无法从代码推出精确 ms。应答目的端口是**请求方源端口**，不是固定回送 60059。

### 1.4 测试要求

可从本机临时端口向控制板 IP 的 UDP/60059 发 `cmd=ping` 并监听本地源端口，亦可尝试子网定向广播；根据抓包判断控制板是否响应广播。`rc3040s_discover.py` 是本轮提供的只读验证脚本，没有运动/配置写操作。

## 2. RotorID 的 EEPROM 初始化、保存、读取

### 2.1 映射与启动

- `0x96D7`: 读取 IAP/非易失地址 `0x001F`，与版本标志 `0x03` 比较；不符合则调用 `0x53E0` 默认初始化。
- `0x940E`: 循环读取配置地址 `0x0000..0x01FF` （512 B），存放 XDATA `0x09A1..0x0BA0`。
- `0x4FB0`: 发现应答取自 XDATA `0x09B1` = 基址 0x09A1 + 0x10，并调用 `0x81FB` 进行 7B→14 HEX 字符编码。
- `0x2380` 附近 `AT+S_ID=` 读取同一识别码位置，调用 `0x81FB` 生成大写 HEX 文本。
- `0x8CE7`: 先擦除 IAP 配置页，再把整个 XDATA 配置镜像写回非易失区（512 B），用于部分配置修改后的整体持久化。

### 2.2 首次初始化 ID 格式

默认配置 `0x53E0` 中：

```
EEPROM 0x10..0x16 <- XDATA[0x0F18..0x0F1E] （7 字节）
EEPROM 0x17..0x1D <- XDATA[0x0F18..0x0F1E] （重复 7 字节）
EEPROM 0x1E       <- 0x00 （C 字符串终止）
EEPROM 0x1F       <- 0x03 （已初始化标志）
```

**已进一步确认来源及输出算法**：启动例程 `0x8786–0x87CE` 使用通用 XDATA 读取函数 `0x06D3`，从 XDATA 地址 `0xFDE0..0xFDE6` 依次读取七个字节并存入 `0x0F18..0x0F1E`。这一寄存器区对应 STC8H 的只读 `CHIPID0..CHIPID6`（<https://www.stcmicro.com/datasheet/STC8H-221114.pdf>，以及 STC 官方技术交流资料 <https://www.stcaimcu.com/forum.php?tid=24057>）。固件 `0x81FB–0x825E` 使用 `0x9738/0x973C` 逐字节取高/低 nibble，并以 0–9、A–F 映射成**两位大写十六进制 ASCII**，循环 7 次。因此 `rotorid` 实际输出为 **14 位大写 HEX 字符**。例如 CHIPID `12 34 56 78 9A BC DE` → `rotorid=123456789ABCDE`。该示例不是某台真实设备的 ID。EEPROM 两个连续七字节槽保存的是**原始二进制 ID**而非文本；本机识别码使用前七字节，第二组初始化同值，其后续用途尚待确认。

`AT+INIT` 对应分支重新执行默认初始化。此操作可能重置 IP、密码等其他设置，**不建议为测试识别码而执行**。

### 2.3 芯片 CHIPID 数据源与十六进制文本编码

- **读取**：`0x8786` 构造 generic pointer `R3=0x01, R2=0xFD, R1=0xE0`；`0x06D3` 对 `R3=1` 执行 MOVX，从 XDATA `0xFDE0+i` 读七个字节（`i=0..6`）。
- **缓存**：原始七字节存入 XDATA `0x0F18+i`。
- **持久化**：首次初始化或重置时，保存到非易失 offset 0x10..0x16，另在 offset 0x17..0x1D 存一份。
- **文本格式**：`0x81FB` 循环 7 次，每次 `0x9738` 取高 nibble、`0x973C` 将其转换为 `0-9/A-F`，后对低 nibble 做同样映射，追加两个 ASCII 字符。结果恰好 14 个大写十六进制字符。
- **限制**：现有硬件不在运行环境中，未读取真实 CHIPID；EEPROM 第二个 7B 槽的可修改性和用途仍需研究。

### 2.4 涉及的 IAP 寄存器

`0x9521`（`C5=0x01`）为 IAP 读；`0x0069`（`C5=0x02`）为 IAP 写；`0x9618`（`C5=0x03`）为 IAP 擦除。需要针对实际 STC8H 型号进一步对应数据手册，不应把 IAP 0x10 解释成 Windows 文件偏移。

## 3. 运动、STOP、查询的命令层

`0x3433` 开始的命令处理器接受从不同链路交付的文本缓冲区。固件中的命令字面量位于 `0xA231..0xA251`。建议在**确认 TCP GS-232 通道**或受控串行测试中使用。请勿在未验证 UDP 控制专用协议前直接把这些文本扔到 UDP/60059。

| 用途 | 输入候选 ASCII | 处理分支与关键调用 | 证据说明 |
|---|---|---|---|
| AZ 绝对目标 | `M181\r` | `0x3455`, XDATA `0x1001..02`, `0x755E` | 代码读取字母后第 1..3 位十进制，以百十个组值；无完整字符有效性验证 |
| AZ/EL 联动 | `W181 030\r` | `0x34E2`, XDATA `0x1001..02`,`0x1009..0A`; `0x755E`,`0x5AEF` | 第 1..3 位 AZ、第 5..7 位 EL，第四位为分隔位（不能证明强制是空格） |
| 查询双轴 | `C2\r` | `0x35D4`, `0x6579` | 文本回复 `AZ=ddd  EL=ddd\r\n`（双空格，三位） |
| 查询 AZ | `C\r` | `0x3624`, `0x7DD1` | 回复 `AZ=ddd\r\n`（三位） |
| 查询 EL | `B\r` | `0x366C`, `0x7E3F` | 回复 `EL=ddd\r\n`（三位） |
| 停 AZ | `A\r` | `0x36B4`, `0x9A35` | 触发 AZ GPIO 停止并使 `XDATA[0x1006]=0` |
| 停 EL | `E\r` | `0x36EF`, `0x9A3F` | 触发 EL GPIO 停止并使 `XDATA[0x1003]=0` |
| 停双轴 | `S\r` | `0x372A`, `0x98A0` | 同时将两轴运行标志清零，并设置电机停止 GPIO 位 |
| AZ 手动 | `L\r`、`R\r` | `0x376A`、`0x37A4` | 调用方向控制函数 |
| EL 手动 | `U\r`、`D\r` | `0x37E2`、`0x3820` | 调用方向控制函数 |

**特别说明三位回复**：`0x704B` 内部格式化五位数字到 XDATA 0x0F20..0x0F24，但 `0x6579`、`0x7DD1`、`0x7E3F` 选择的字符串起点是 `0x0F22`，因此输出的是**后三位**，例如：

```
C2\r  →  AZ=180  EL=030\r\n
C\r   →  AZ=180\r\n
B\r   →  EL=030\r\n
```

以上是静态数据流恢复的**预计字节格式**，不是实机抓包记录。标准 GS-232 驱动通常能复用指令语义，但应为此固件另行支持 `AZ=`/`EL=` 的实际回复格式。

### 3.1 实际角度及指令目标在 RAM 中并非同一字段

- `0x1001..0x1002`：AZ 目标角度。
- `0x1009..0x100A`：EL 目标角度。
- `0x1007..0x1008`：AZ 实测/回报角度。
- `0x1004..0x1005`：EL 实测/回报角度。
- `0x1006`：AZ 运行状态/控制标志，停止时清零。
- `0x1003`：EL 运行状态/控制标志，停止时清零。

这是避免 SkyRoof 把“已下发目标角度”误认为“云台已经到位”的重要依据。

### 3.2 UDP 发现与 GS-232 数据通路不能混为一谈

已验证：Socket 2（UDP/60059）经 `0x8E0A` 转到 `0x4E62`，其已确认行为是 `cmd=ping` / `cmd=pong`。调用 GS-232 解析器 `0x3433` 的点在 `0x4A3A`、`0x5DCE`、`0x8126`、`0x885A`，其中 `0x8822` 是 Socket 3 的独立接收处理路径。**尚未在本轮完整解析 Socket 3 的开启端口和模式**。因此，不能据此宣称 UDP/60059 本身支持 `M/W/S/C2`。最稳妥的实机路径仍是先核对 TCP 60020 后再测试。

## 4. 与 NRL2 的关系和剩余工作

本 MCU 镜像中找到了 `cmd=ping`、`cmd=pong`、`rotorid` 与 GS-232 控制指令；没有直接识别出 `NRL2` 明文封装实现。开源 NRL 服务器（`hicaoc/nrllink`）有 48B 头部和 Type 6/10 转发逻辑，但不能在没有抓包/另一 MCU 固件时把 NRL2 头机械地加在 `M181\r` 前直接发送到 UDP/60059。NRL2 中认证/会话、设备分组和目标寻址仍需另行验收。

后续精确验证顺序：

1. 本地仅发 `cmd=ping` UDP/60059，抓完整 `pong` 原始字节，记录源 IP、源端口、末尾换行和时延；多网卡时分别抓包。
2. 同网段两台设备读取 `rotorid`，对比唯一性。仅查询，不执行 `AT+INIT`。
3. 在 TCP/60020 无负载连接上先发 `C2\r`，验证三位、双空格、CRLF；再测试 `C\r`、`B\r`。
4. 做实际运动测试前确认 STOP 在本地/远端不同网络故障下能触发物理停机，安全限位有效。
5. 对 DTrac 使用 NRL 模式做局域网/公网同步抓包，寻找 `NRL2` 包头和 Type 6/10 负载，建立包字段与 GS-232 命令的对应关系。
