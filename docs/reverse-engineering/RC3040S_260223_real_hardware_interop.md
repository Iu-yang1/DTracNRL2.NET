# 实机互操作证据：2026-10-24 11:25:50 +08:00（来自操作者提供的诊断日志）

本记录对应真实 RC-3040S 控制板，不等同于既有
`RC_3040S_67S_8H_251217` 固件二进制的静态逆向。

## 已实机确认

- TCP/60020：连接成功；通过 GS-232 `C2\r` 只读查询返回 `AZ=0.0, EL=0.0`。
  证明位置查询有效，但不代表在本次会话进行了电机移动。
- TCP/60030：连接成功、RFC 6455 WebSocket Upgrade 成功。
- 连接后等待 2 秒没有主动文本；在新的 WebSocket 会话上发送 `C2\r`，
  随后收到文本形如 `RC_3040S_67S_8H_260223_C <14-hex-device-id>\r\n`。
  **明确不是角度格式**；不能排除是延迟欢迎/设备标识帧，因此尚不能认定它是 `C2` 的语义应答或配置命令 ACK。
  此标识提示用户设备固件为 **260223_C**，而此前固件静态逆向使用 **251217**；
  不能把旧版命令/DEMO、计时器或心跳行为一概推广到这个硬件版本。
- UDP/60059：广播 `cmd=ping\n` 在测试窗口内未收到该 IP 的答复；**向设备 IP 单播相同字节得到有效 75B PONG**，
  其报文文本为 `cmd=pong&type=RC-3040S&ip=192.168.001.009&port=60020&rotorid=<14hex>`。
  报文表明设备使用三位十进制 IPv4 八位组。无线电电脑的 SDK 旧版返回 RAW，
  因其 `IPAddress.TryParse` 不能可靠处理带补零八位组。已实现显式十进制解析。
  用户真实 RotorID 不在本报告或回归测试中重现。

## 已改进的 SDK

- `Rc3040sDiscovery.TryParseDecimalIpv4`：十进制（不使用历史八进制语义）的 4 个八位组，允许 1–3 位，范围 0–255。
- `Rc3040sDiscovery.DiscoverAtAsync`：指定目标 IPv4 发 UDP/60059 `cmd=ping\n`，不需要广播成功。
- `Rc3040sFirmwareBanner.TryParse`：独立识别 WebSocket 固件版本文本，并默认仅输出打码后的设备 ID；不会误归类为位置值。
- 诊断 EXE v3：保留明确授权的只读 `C2`；对固件标识区别显示、避免日志暴露完整硬件 ID。
